# Ticket 10 — explicit tuning apply/reset matrix

Baseline: integration `2a39967` (ticket 09 ledger); pinned Jev Pilot 0.12.1 `5d27135b34edf81b40c0bf1df01ae401f6b72ea7`, `hooks/tuning.ts` (ranges, `since`, apply/reset), `hooks/ledger.ts` `suggestions()` (proposal conditions, `MIN_TURNS_TO_SUGGEST=20`) and `tests/tuning.spec.ts`. This matrix precedes the tests. Seams: pure tuning module, and the official Pi 1.4.0 RPC CLI with the packed extension, a local System One fixture and a local model fixture.

Storage: `<Pi agent dir>/jev-pilot/tuning.json` (`{ version: 1, values, since }`), a sibling of the ledger and the Pi counterpart of upstream's plugin-store key `tuning`. It is user-level state shared by the sessions of one Pi agent directory and read afresh at each decision by the main session and its worker-plan decisions; execution children load only the child marker extension and never read or write it. Evidence is ledger entries with `at > since`. Base values are the upstream defaults with `JEV_TIMEOUT_MS` as the base timeout; learned values overlay them.

Adaptations, all from the ledger shape that ticket 09 owns: upstream's mid-turn "raised" signal does not exist (mid-turn escalation is excluded), so trouble at a cheap start is a user correction only. `/jev tune reset` persists `{ values: {}, since: <now> }` rather than deleting the file, so the evidence that produced the cleared change cannot re-propose it after a reload (upstream kept that only in memory).
