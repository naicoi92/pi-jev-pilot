# Pi Upstream Multi-Provider Model and Effort Routing — Research

**Research date:** 2026-10-21  
**Scope:** architecture recommendation only; no implementation, credentials, paid calls, installs, or settings changes.  
**Local context:** prior scope is public Pi package, System One configurable default Jev, Pi-registry model aliases, effort/main/subagent routing, skills/strategy/quality/design, standard/budget/junior-lead, ledger/tuning. Strategy advice is not an engine adapter. Preserve bounded context; fail-open on classifier/service faults while respecting abort. Do not bake in Claude tier semantics.

## Executive result

**Recommendation (evidence-based design direction, not an implementation):** use a Pi virtual model as an optional/explicit *default Jev selection seam* where per-request routing is desired; have Jev classify bounded task attributes (not guess model IDs), then apply a deterministic policy to **user-curated execution profiles**. Profiles reference qualified model identities from Pi's live authenticated registry and carry verified capabilities and allowed thinking levels. The selector must validate an eligible profile against the current registry/auth, resolve its physical `provider/model`, choose a Pi-supported thinking level, and record requested and effective decisions/outcomes. If the classifier fails/times out, use a deterministic safe profile/fallback; if the request's abort signal fires, do not swallow it. Do not call a price or model-name heuristic a capability assessment.

Suggested decision path:

`user-configured default/explicit override → curated execution profiles → registry/auth/capability eligibility → bounded task attributes → profile selection → deterministic policy (risk/role/effort/limits) → physical model + supported thinking → Pi dispatch → ledger (requested/effective/outcome)`

This is preferred over both a fixed role→one model mapping (simple and can classify tasks into roles, but each role has only one model and therefore fewer alternatives under image/context/auth constraints) and Jev directly choosing from the full authenticated registry (flexible in appearance, but model IDs and price are not dependable capability data and classifier cannot establish reliable cross-provider rankings). It separates classification and policy, preserves eligibility as a safety invariant, and keeps per-install model knowledge with the user rather than the classifier.

**Upstream architecture fit is unusually strong in current Pi:** the latest stable npm dist-tag observed was `@earendil-works/pi-coding-agent@1.3.0`, released 2026-10-15. Its virtual-model API routes *each physical request* to a registry model + thinking level, passes route reason/previous/failed/state/message history/abort signal, persists branch-local JSON state, clamps the requested thinking level to the physical model, validates that the route is physical and authenticated, and records the physical response identity/effort/usage. Pi also supplies a first-party `jev-router.ts` example. This is the appropriate seam for per-request main-model routing rather than changing model in the middle of a turn.

**Adapter boundary:** `pi-subagents@0.80.0` is a current, plausible external orchestration/adapter integration candidate (its package declares compatibility with Pi coding-agent `>=1.2.0`; Pi 1.3.0 is within range). It supports per-run model/thinking configuration and reports requested/resolved child model and usage in its own accounting. But it is not itself the model-selection policy: its docs say each launch chooses one model, errors/429s return from that model, and another attempt requires a later explicit launch. Its general `external-cli` runners reject model/thinking fields; only specifically code-owned Claude Code adapters translate them into that engine's `--model`/`--effort`. **Do not assume general external-engine model/effort injection is available**: adapter-specific contract, cancellation propagation, and usage reporting must be verified for the chosen engine. Native Pi children managed by this external package fit the user's chosen external-package adapter boundary and offer shared registry/model/thinking compatibility. The user did not require a non-Pi execution engine.

**No user model IDs are chosen or recommended here.**

## What Pi exposes and guarantees

### Model registry, identity and catalog

Pi’s `Model<Api>` distinguishes a model by `provider` plus `id` (the helper `modelsAreEqual` compares both). The chat model carries `name`, `api`, `baseUrl`, `reasoning`, optional `thinkingLevelMap`, `input` modalities, cost rates, `contextWindow`, `maxTokens`, and compatibility metadata. Pi's model registry exposes all catalog models and available/authenticated models separately, supports `find(provider,id)`, and exposes registered providers and model-type registries. Registry `getAvailable()` is an auth-configured snapshot/check, **not a live provider health/quota probe**. `hasConfiguredAuth` does not prove a credential will still work or that account quota/rate limits permit a request. [Pinned source: `packages/ai/src/types.ts` lines 839-864; `packages/coding-agent/src/core/model-registry.ts` lines 64-87; `packages/coding-agent/src/core/model-runtime.ts` `hasConfiguredAuth`/`resolveModel` around 551, 1003-1033; published tarball `dist/core/model-registry.d.ts`.] 

Models and model limits can be user-configured/overridden through Pi’s model registry/configuration; Pi docs recommend use of the built-in catalog when supported and custom `models.json` only for endpoints/models it does not already cover. The model catalog includes identity, protocol, supported input, reasoning metadata, prices, context/output limits, and provider compatibility details. **No general `supportsTools` field is present in the chat `Model` interface**, so a Jev profile must not infer tool reliability just from model identity/price. Use user curation/verified profile declarations and, if appropriate, tests/probes under explicit operator control. Pi's public model-registry methods for `find`, `getAvailable`, `hasConfiguredAuth`, classifier calls, and image models are available via `ctx.modelRegistry`. [Pinned tarball `docs/models.md`; pinned Pi types/model registry above.]

Model catalog data is useful for **eligibility constraints** (auth configured, image input, context/max output, reasoning support, Pi's supported thinking choices), not proof of quality or task success. Capability claims about tool use, code quality, instruction following, design taste, long-context quality, and provider reliability require curated/tested metadata; pricing expresses money per token, not ability.

### Thinking levels are a Pi abstraction, not universal effort semantics

Pi’s public level ladder in 1.3.0 is `off`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`. `thinkingLevelMap` maps selected Pi levels to provider/model-native values; a `null` entry marks unsupported. `getSupportedThinkingLevels(model)` returns only available levels and `clampThinkingLevel(model, requested)` finds an effective supported level. Provider implementations translate the abstract level per API/provider/model; the numeric or semantic amount of reasoning behind a label is not comparable across providers. Do not reuse a fixed “low/medium/high means Claude tiers” assumption, or equate a level label between vendors.

There is an important nuance: a missing map entry generally relies on provider defaults for levels except `xhigh`/`max`, which Pi only treats as supported when explicitly mapped. Pi guarantees its own clamp, not identical effort behavior or successful vendor interpretation for every compatibility endpoint. For ledger clarity, store requested Pi level, effective/clamped Pi level, and provider-native level if reliably available; do not claim equivalence across providers. The model's `reasoning` boolean and level map are catalog facts, not a benchmark. [Pinned source: `packages/ai/src/models.ts` lines 1228-1265; `packages/ai/src/providers/model-schema.ts` lines 3-15; `packages/ai/src/types.ts` lines 451-482, 570-596, 839-864; provider translation source e.g. 1.3.0 Anthropic/OpenAI/Google provider modules and their `thinkingLevelMap` logic.]

### Extension session controls: useful but global selection, with persistence risk

`ExtensionContext` provides current model, thinking level, model registry, `signal`, `abort()`, context usage, compaction trigger, and read-only session history. `ExtensionAPI` can call `setModel(model)` and `setThinkingLevel(level)`, and in 1.3.0 can register/unregister providers and virtual models. In 1.3.0, `AgentSession.setModel(model, { persist?: boolean })` and `setThinkingLevel(level, { persist?: boolean })` default to **session-only**; `persist: true` changes global defaults. However the ordinary extension API's `setModel` and `setThinkingLevel` methods do not expose the `persist` options. The 1.3.0 `setModel` still records a model-change in session, and applies model-specific thinking/clamping. This API mutates current session selection, so it is not as clean as a virtual router for request-specific choices. Never interpret a classifier choice as consent to change the user's default or write settings. [Pinned tarball `dist/core/agent-session.d.ts` lines 189-200, 654-686; `dist/core/extensions/types.d.ts` lines 1770-1810; source `agent-session.ts` corresponding `setModel`/`setThinkingLevel` and `ExtensionContext`.] 

### Virtual models: strongest main-model seam

`pi.registerVirtualModel` adds a selectable catalog entry (appears in `/model`, `--model`, scopes, settings). That selection can represent Jev/Auto while each actual API request uses a resolved physical catalog model and a separate supported thinking level. The API contract is explicit:

- `ModelRouteRequest`: selected virtual model and Pi thinking level; `reason` = `user | continuation | retry | direct`; latest successful `previous` physical model/level; failed physical model/level/message for retry; branch-local `state`; bounded? full Pi conversation `messages`; `signal`.
- `ModelRoute` returns a physical model and requested thinking level; Pi validates the target exists, is non-virtual, and its provider has configured credentials, then clamps thinking against target capabilities. Invalid/missing/unauthenticated physical route throws and the request errors.
- State is JSON serializable and written to the session branch; it follows tree navigation/fork and compaction. A state update is recorded before dispatch, even if the downstream request then fails. `direct` requests (e.g. compaction summary) have no persisted state.
- Pi route reasons permit deterministic behavior: keep a prior physical model through tool continuation/cache-sensitive turns, apply a fresh route on user turn, inspect `failed.message` for retry policy, and route direct calls conservatively. Official docs explicitly recommend returning `previous` on continuation and `failed` on retry to preserve prompt caches/signatures, but allow switching on a retry when it is justified.
- **Router exceptions are fail-closed, not fail-open.** The adapter/router must catch classifier/provider faults itself and return a valid deterministic fallback route. It must still propagate `signal` abort rather than treating cancellation as a classifier failure. `resolveModel` throws if a classifier callback route is virtual/missing/unauthenticated; a stale catalog or revoked auth must be handled before returning a route.
- Assistant messages record physical `provider`, `api`, `model`, `thinkingLevel`, and usage; virtual selection remains separate in session history. Pi displays virtual→physical routing and physical-model usage/cost. Context and auto-compaction limits use the actual physical model's limits after first reply; before first reply, virtual limits may be declared. Virtual catalog `input` defaults to text/images but physical routes without image capability receive placeholders; eligibility should prevent inappropriate image routes rather than depend on placeholders.

This is per-request route injection **in host core**, not a hook that can be simulated by mutating process globals. The 1.3.0 extension API exports `registerVirtualModel<TState>`. Full type contract in exact tarball `dist/core/virtual-models.d.ts` lines 26-116; `dist/core/model-runtime.d.ts` lines 120-141; `dist/core/extensions/types.d.ts` lines 1394-1411; official pinned docs `docs/virtual-models.md`. Source lines in release commit: `packages/coding-agent/src/core/virtual-models.ts` lines 50-104; `model-runtime.ts` lines 1003-1039; `agent-session.ts` lines 817-843.

### Usage, fail/retry, compaction and cancellation

Pi `AssistantMessage` names requested physical provider/model, optional provider-reported response model, exact native thinking level when known, Pi thinking level for loop-managed calls, usage/cost, stop reason, response ID, and diagnostics. Usage records input/output/cache read/cache write, optional provider reasoning tokens, total tokens, and cost components; provider reporting may be incomplete. Pi session accounting adds assistant usage by physical model, and `/session` reports physical model cost. For reliable Jev routing audit, preserve classifier decision latency/failure separately from model-turn usage and record planned physical choice vs actual assistant-message model; do not assume a requested route ran if it failed or provider auto-routing changed it. [Pinned tarball `packages/ai/src/types.ts` locations 451, 570 and `packages/coding-agent/src/core/agent-session.ts` session usage aggregation; docs `docs/virtual-models.md`.] 

`ctx.signal` is the request abort signal. `AgentSession.abort()` requests abort, aborts retry, compaction, and branch summary, and waits idle. Pi's virtual router can call a classifier with that signal; implement classifier latency timeout with a bounded abort controller linked to parent signal. A non-abort classifier failure/timeout should return fallback profile, whereas abort should stop. Distinguish that classifier fail-open behavior from Pi's downstream provider policy: virtual route errors fail the request; automatic retry handles selected transient errors and context-overflow recovery, with route reason `retry`. Model routing state lets a router preserve chosen physical model on continuation and either preserve or reconsider model on retry. Do not silently start a second provider request after an error; define retry authorization/idempotency/budget policy. [Pinned source `AgentSession.abort()` lines 2464-2474; virtual-model contract as above; tarball `docs/virtual-models.md` route/retry section; `agent-session.d.ts` retry/compaction docs.] 

`turn_end` exposes assistant message and tool result messages at turn boundary, and `before_agent_start` exposes raw user prompt and images. `before_provider_request` can replace payload; `after_provider_response` exposes status/headers. These are observability/input seams, but don't replace virtual-model routing. The router receives the full conversation, so Jev should apply bounded minimization itself (prior report's prompt-keyed context design is not the route contract). Preserve privacy: avoid sending full tool bodies/output unnecessarily. [Pinned `packages/coding-agent/src/core/extensions/types.ts` lines 325-350, 901-957, 1065-1072, and official docs.]

## Architecture options compared

| Option | Benefits | Costs/risks | Assessment |
|---|---|---|---|
| **Fixed role → one model profile** | Simple, low decision latency; static main/worker/reviewer choices easy to audit; fits basic Pi subagent frontmatter/overrides. | Task classification can choose different roles, but each role maps to only one model. Alternative image/context/auth constraints require additional mappings or exceptions. Static effort is a limitation only if the mapping does not include a demand-dependent thinking policy; profile staleness/auth failures remain. | Good initial safety fallback and manual override, poor complete routing model. Retain as deterministic fallback and explicit user choice. |
| **Curated candidate execution profiles** | User owns model identity and tested capability claims; eligibility removes unavailable/unsupported profiles before classification; supports cross-provider profiles without name heuristics; policy chooses main/worker profiles and effort; easy audit and standard/budget/junior-lead overlays. | Requires schema/editor path, validation and maintenance; capability data is user-curated and may stale; model/service drift needs health/probe lifecycle; tool-call quality is not an official field. | **Preferred target.** Keep candidate lists intentionally small and explicit, no automatic benchmark claims. |
| **Automatic choice over full authenticated registry** | Broad catalog coverage and minimal upfront profile curation; can discover newly added models. | Auth availability does not establish working quota, image/tool behavior, task capability or cost comparability; model IDs/metadata may be missing/user-inaccurate; large choice roster burdens classifier; safety/latency/privacy/cost and cross-provider comparability are hard; no safe unknown-model inference. | Reject as default. Could support opt-in discovery assistant that proposes profile changes for user confirmation, with no automatic selection until verified. |

### Classify task attributes first vs choose profile directly

**Recommend task attributes → deterministic policy/profile selection.** Jev should answer small typed, bounded questions about task shape/constraints (e.g. read-only vs change; specified vs open-ended; known vs unknown cause; risk; image attached; likely context size; role/main vs worker) and remain model-ID agnostic. Deterministic policy intersects those attributes with the eligible, user-curated candidate profiles and applies user override, risk guard, context/visual/tool requirements, effort capability/clamp and cost ceiling. This is more testable and model-provider neutral, easier to explain in a ledger, and avoids asking Jev to guess unknown catalog entries. It also keeps policy invariants outside probabilistic output.

**Direct classifier choice among eligible profile IDs** is a possible bounded optimization only if the profile roster is small and each entry has clear user-verified descriptions. The classifier still cannot establish accurate cross-provider quality/price/capability from IDs. A failure/low confidence/ambiguous profile must fall back deterministically. Prefer classifier outputs as task attributes; do not let it emit arbitrary model IDs or unvalidated effort strings.

Potential profile metadata should be explicit rather than inferred: `provider`, `modelId`, `auth/availability observation`, user-curated capability tags (`text`, `image`, verified tools, code editing, design judgment, long context, etc.), context/output limits from registry, supported thinking levels from Pi, user-stated budget/role fit, provenance/last verified date, and fallback. Keep Pi-catalog facts distinct from human/bench claims.

## Proposed deterministic selection details (recommendation, not approved specification)

1. Eligibility precedes ranking: approved profile, main/worker scope, configured auth, input modalities, context/output constraints, and allowed thinking. Tool-use suitability is an explicit curated declaration with provenance, not a native `supportsTools` catalog fact. Registry validation is not live health probing.
2. Jev classifies work shape: read/write, spec clarity, known/unknown cause, judgment demand, risk and verification. Image presence is read from actual input; context fit uses runtime estimation, not classifier guesses.
3. Filter profiles by required task suitability. Among suitable profiles, apply explicit user priority; a documented stickiness rule can retain the current eligible profile within the same preference class to avoid cache churn. If unresolved, use an explicit configured default or ask, never invent capability/price scores. Priority is a user preference, not an empirical ranking.
4. Jev returns reasoning demand, not a globally portable provider effort. Each profile maps demand to supported Pi thinking levels, with an explicit ceiling. Multiple demand levels may map to the same level or `off`; if the profile cannot meet a hard task requirement, it is ineligible.
5. Pi clamp searches upward first, then downward when the requested level is unsupported. It can increase effort. Strict ceilings must be enforced before dispatch with supported-level mappings; record requested and effective levels afterward.
6. Classifier fail-open does not authorize automatic cross-provider retries of coding requests. Worker health/fallback remains outside selected scope.

## Scenario matrix

The routing result is an execution-profile + supported Pi effort; this matrix intentionally avoids provider or model IDs.

|---|---|---|---|
| Read-only lookup | Explicit information retrieval/local inspection; no writes; bounded context; no image requirement. | Eligible low-cost read/research profile, modest supported thinking; preserve user pin. | Record requested/effective profile; do not auto-select a model solely from “cheap”. |
| Specified coding | Clear acceptance criteria, localized/mechanical change, tests/verifiable outcome. | Standard implementation profile; supported moderate thinking; main vs worker routed according to host action. | Strategy may advise delegation but must not spawn unless adapter/tool does it. |

## Fail-open, abort, policy and ledger invariants

1. Classifier timeout/service/auth/schema failure → use configured deterministic default/last-valid-safe profile, with no setting mutation; expose/log degraded routing. The fallback is not a guessed model tier. If no eligible profile remains, ask/stop rather than select an unvalidated model.
2. `signal.aborted` → propagate abort; never convert explicit cancellation into fallback and continue generation.
3. Preserve explicit per-request/user model choice; default Jev should be opt-in through selected/default alias and not hijack manually chosen physical models.
4. Validate candidate against live runtime registry identity/provider+id and auth status immediately before returning `ModelRoute`; verify actual assistant response `provider/model` afterward.
5. Record classifier and route requested/effective details: route ID, profile ID/revision, policy version, task attributes/confidence, eligibility results, requested and effective Pi effort, physical provider/model dispatched, response model if different, route reason, retry/continuation relationship, outcome/stop reason, usage/token/cost when supplied, latency/timeouts, abort, compaction. Keep sensitive prompt content out of persistent ledger; store minimized signals only. Separately measure classification calls/usage if the provider exposes it.
6. Tuning can adjust policy thresholds only from attributed evidence; do not claim counterfactual model quality or savings from single-run logs. Use explicit human approval for any persisted tuning/settings change.

## Blockers and unresolved verification before implementation

- **Exact external-package integration seam has not been validated.** Native Pi children managed by pi-subagents are in scope; a non-Pi engine is not required. pi-subagents demonstrates per-launch model+thinking injection, but transparent interception of ordinary and workflow launches without replacing explicit user overrides still needs source verification. Per-launch parameters alone do not prove a supported routing extension hook. If another execution engine is chosen later, its adapter must explicitly provide model/effort support. Confirm adapter cancellation closes the process/request, and captures actual model/effective effort/usage/errors.
- Catalog auth means configured credentials, not usable quota or working health; a route can still fail for expiry/rate limit/outage. Policy must specify fallback/retry ceiling and whether cross-provider retry is safe.
- Pi `Model` lacks general tool-support/capability quality declarations, and model metadata can be missing or user-overridden. User curation or verified profile probes are required. The included profile generator/prober is not a universal cross-provider performance benchmark and uses small no-tools checks.
- No live model/API calls or paid probes were made. No live auth, quota, provider thinking translation, multi-provider tool calling, timeout/cancel, compact/retry, adapter E2E, cost report, or child lifecycle verified.
- Pi virtual routing calls Jev at request time, can add first-token latency, and gets full conversation messages unless Jev bounds/minimizes them. Classifier input privacy/budget controls need explicit design. First-party example truncates user prompt to 16,000 characters but that is example policy, not a core guarantee.
- Direct/compaction calls use `reason=direct` and have no branch state; pick a conservative valid model/effort and ensure fallback for summary request failures without creating an auto-compaction loop.
